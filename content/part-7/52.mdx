# 数据库是什么——从 Excel 到 SQL

> 本章介绍关系型数据库：它用表组织数据，并提供查询、约束和事务——你用过 Excel，就理解了一大半。这一章讲清数据库和 SQL 到底是什么，再带你用 Racket 把它跑起来。

这一章要回答三个问题：数据库到底是什么、SQL 是什么、在 Racket 里怎么用。前两个问题不依赖任何编程知识——如果你是那种“工作中要用到数据、但不理解编程”的人，前两节读完你就懂了数据库的本质。

## 先回到一个朴素的需求：数据要存下来，还能查

你写过这种程序吧——几条配置、一点状态、几张待办事项，程序关掉下次还想留着。最直观的做法是把数据写进文件。Racket 里这件事简单到令人发指：

```racket
(require racket/file)
(define path (make-temporary-file))
(dynamic-wind
 void
 (lambda ()
   (call-with-output-file path
     (lambda (out) (write '(("买牛奶" . #f) ("写代码" . #t)) out))
     #:exists 'truncate)
   (call-with-input-file path read))
 (lambda () (delete-file path)))
;; => '(("买牛奶" . #f) ("写代码" . #t))
```

`write` / `read` 这对函数直接把 Racket 的数据结构序列化进文件——一个列表进、一个列表出，连 JSON 都不用。临时文件仅用于演示序列化往返，结束后自动删除。实际持久化应选定应用数据路径，考虑写入中断、原子替换和备份。

这套方案在数据量小、结构简单时近乎完美。但某一天你会撞墙：你想知道“哪些任务还没做完”，于是把整个文件读进来，`filter` 一遍，再把结果用掉。数据量一大，每次都全量读进内存，只为了筛那么几条。

这时候你开始想：能不能“只读没做完的那些”？也就是说，数据得能被按条件查询，而不是整体搬回家再翻。

## 文件的天花板，正好是数据库的地板

这个简单列表文件的存储方案没有独立的查询与索引机制。文件也可以设计索引和随机访问，但这需要额外实现。这把两件事混在了一起：数据怎么存，以及怎么找。

数据库解决的正是这件事——它把“找”下沉成一个独立的、声明式的动作。你只要说“我要状态为未完成的所有任务”，怎么高效地找到它们是数据库的事，不是你的事。

但一提到数据库，很多人脑子里冒出的是另一套画面：下载安装包、配端口、建用户、起服务进程、再写网络连接代码。这套恐惧来自一个误解——把“数据库”和“数据库服务”画了等号。下面先把概念理清，这个误解自然就消了。

## 数据库的核心，是一张表

抛开所有技术细节，关系型数据库的重要抽象是表。其他类型的数据库可能采用文档、键值或图等模型。

如果你用过 Excel，你已经理解了。一张 Excel 表是什么样的？

| 标题 | 完成 | 创建日期 |
|------|------|----------|
| 买牛奶 | 否 | 2026-08-01 |
| 写代码 | 是 | 2026-08-01 |
| 还书 | 否 | 2026-08-02 |

数据库里的表就是这个样子：

- **表**（table）：一张表，对应一个 Excel 工作表
- **列**（column）：表的结构，对应 Excel 的列头——“标题”“完成”“创建日期”这些
- **行**（row）：一条具体的数据，对应 Excel 的一行——“买牛奶、否、2026-08-01”

就这么简单。数据库的“表”和 Excel 的表，在概念上几乎一模一样。差别只在于：电子表格也支持筛选与计算；关系型数据库还提供查询语言、约束、事务和并发控制。实际性能取决于查询、索引和数据规模。

理解了“表 = 结构化的数据”，你就理解了数据库的本质。它不是什么高深的服务器技术，就是一张能被程序快速查询的表。

## SQL：和表格对话的语言

怎么和这张表“对话”？用一种叫 SQL（Structured Query Language，结构化查询语言）的语言。SQL 是专门为表格数据设计的——你用它告诉数据库“我要什么”，数据库替你去找。

SQL 看起来像英文句子，核心只有四个动词，对应数据的四种基本操作：

| 动词 | 干什么 | 对应日常操作 |
|------|--------|------------|
| `SELECT` | 查找：按条件读出数据 | 在 Excel 里筛选 |
| `INSERT` | 插入：添加一行新数据 | 在 Excel 里新增一行 |
| `UPDATE` | 更新：修改已有数据 | 在 Excel 里改某个格子 |
| `DELETE` | 删除：去掉数据 | 在 Excel 里删行 |

记住这四个动词，你就掌握了 SQL 的骨架。来看真实的例子。假设有一张 `tasks` 表（标题、是否完成），这四个动词长这样：

```sql
-- 查：找出所有没完成的任务
SELECT title FROM tasks WHERE done = 0;

-- 增：添加一条新任务
INSERT INTO tasks (title, done) VALUES ('学 Racket', 0);

-- 改：把"买牛奶"标记为完成
UPDATE tasks SET done = 1 WHERE title = '买牛奶';
-- 如果标题重复，这会更新所有匹配行；实际编辑单条任务通常使用 id

-- 删：删掉所有已完成的任务
DELETE FROM tasks WHERE done = 1;
```

你看，每条 SQL 都像一句简短的英文：`SELECT title FROM tasks WHERE done = 0`，直译就是“从 tasks 表里，选出 done 等于 0 的那些行的 title”。SQL 之所以设计成这样，就是为了让“我要什么数据”这件事尽量接近自然语言——你说清要什么，怎么找交给数据库。

有个细节值得强调：`SELECT` 里你只说“要什么”（哪些列、什么条件），没说“怎么找”。如果是一百万行数据，数据库自己决定怎么高效地翻、用不用索引、从哪开始找——这些“怎么找”全是数据库的事。

这种“你声明要什么，机器负责怎么做”的风格，和函数式编程里用 `filter`、`map` 的思路是一脉相承的。**SQL 是一种声明式的语言**，这正是它强大的根源。

## SQLite：长得像文件，干活像数据库

概念理清了，现在上手用。但“数据库”那个运维画面又来了——难道真要装一个服务？

不用。有一种数据库叫 SQLite，它的存在就是为了把这个门槛抹平。SQLite 是嵌入应用进程的关系数据库引擎，通常把数据保存在文件中，不需要单独运行数据库服务器。在 Racket 里用 SQLite，只需要三步，全程不装任何服务：

```racket
(require db)

;; 1. 创建独立的内存数据库，每次运行从空库开始
(define conn (sqlite3-connect #:database 'memory))

;; 2. 建表、插数据、查询——全是 SQL，通过同一个连接
(query-exec conn
  "CREATE TABLE IF NOT EXISTS tasks (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    done INTEGER NOT NULL DEFAULT 0 CHECK (done IN (0, 1)))")

(query-exec conn
  "INSERT INTO tasks (title) VALUES (?)" "学 Racket")

(query-list conn "SELECT title FROM tasks WHERE done = 0")
;; => '("学 Racket")

;; 连接暂时保留，供下一节查询练习使用。
```

注意几件事：没有 `apt install`，没有 `systemctl start`，没有端口号，没有用户密码。上述内存数据库在连接关闭后消失。如果希望跨重启保留数据，可将连接改为 `(sqlite3-connect #:database "app.db" #:mode 'create)`；请勿删除真实数据库。数据库打开时可能还有日志或 WAL 文件，备份应采用 SQLite 支持的一致性备份方式，而非随意复制正在写入的主文件。文件数据库与内存数据库的查询接口相同，但生命周期不同。

这正是 SQLite 为什么适合入门——它去掉了数据库里所有属于“服务”的部分，只留下“能查询”这个核心。你刚才学到的“表”“SQL 四个动词”，在 SQLite 里和在那些重型数据库（PostgreSQL、MySQL）里具有共同的基础概念，但类型、SQL 方言、占位符和并发行为存在差异。数据库的基本概念是通用的，SQLite 只是让你用最低成本摸到它。

从使用体验上倒推它的身份：对刚入门的程序来说，SQLite 是完整的嵌入式关系数据库引擎，而不仅是文件格式。理解了这层身份，新手对数据库的恐惧就没了。

## 把 SQL 结果变成 Racket 数据

`query-list` 只是查询的一种形式。更多时候你要拿回整行数据，而不只是一个值。`db` 库提供几种查询函数，对应不同的需求：

```racket
;; 拿回一个值（单行单列）
(query-value conn "SELECT COUNT(*) FROM tasks WHERE done = 0")
;; 首次运行且仅插入一条任务时，结果为 1

;; 拿回一行（作为向量）
(query-row conn "SELECT * FROM tasks WHERE id = 1")
;; => #(1 "学 Racket" 0)

;; 拿回多行（每行是向量，整体是列表）
(query-rows conn "SELECT title, done FROM tasks")
;; 首次运行：'(#("学 Racket" 0))

;; 拿回某一列的所有值（列表）
(query-list conn "SELECT title FROM tasks")
;; 首次运行：'("学 Racket")

;; 暂时保留连接，供下面的参数化查询练习使用。
```

注意一个关键细节——前面插入数据用的是参数化查询：

```racket
(query-exec conn "INSERT INTO tasks (title) VALUES (?)" "学 Racket")
(disconnect conn)
```

那个 `?` 是占位符，真正的值 `"学 Racket"` 作为单独的参数传进去。**使用参数化查询传递用户输入，不要用 `string-append` 把值直接拼进 SQL 字符串。**

直接拼接会留下 SQL 注入的漏洞——拼接可能改变查询语义或引发语法错误，实际影响取决于数据库接口与权限。参数化查询将 SQL 结构和参数值分开传递，这是用数据库的一条铁律。

## 事务：多个修改作为一个整体

在同一个数据库连接上，可以用 call-with-transaction 将多个操作组织在一起。正常返回时提交；发生异常时回滚。下面使用独立的内存数据库练习，不会修改已有文件。

```racket
#lang racket/base
(require db)
(define c (sqlite3-connect #:database 'memory))
(dynamic-wind
 void
 (lambda ()
   (query-exec c "CREATE TABLE tasks (title TEXT NOT NULL)")
   (call-with-transaction c
     (lambda ()
       (query-exec c "INSERT INTO tasks VALUES (?)" "买牛奶")
       (query-exec c "INSERT INTO tasks VALUES (?)" "还书")))
   (displayln (query-value c "SELECT COUNT(*) FROM tasks")))
 (lambda () (disconnect c)))
```

预期输出 2。事务不是所有外部副作用的回滚机制，它保护数据库中参与事务的操作。第 55 章的 Loom Taskboard 将事务用于表单提交后的持久化。

## 动手验证：约束与事务回滚

```racket
#lang racket/base
(require db rackunit)
(define conn (sqlite3-connect #:database 'memory))
(dynamic-wind
 void
 (lambda ()
   (query-exec conn "CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT NOT NULL UNIQUE)")
   (query-exec conn "INSERT INTO tasks (title) VALUES (?)" "it's fine")
   (check-equal? (query-value conn "SELECT title FROM tasks WHERE title = ?" "it's fine") "it's fine")
   (check-exn exn:fail:sql?
     (lambda ()
       (call-with-transaction conn
         (lambda ()
           (query-exec conn "INSERT INTO tasks (title) VALUES (?)" "temporary")
           (query-exec conn "INSERT INTO tasks (title) VALUES (?)" "it's fine")))))
   (check-equal? (query-value conn "SELECT COUNT(*) FROM tasks") 1))
 (lambda () (disconnect conn)))
```

保存为 database-test.rkt，执行 raco test database-test.rkt，预期三项检查通过。第二次插入已有标题违反 UNIQUE 约束，事务回滚第一次插入的 temporary，但事务开始前的记录仍然存在。此处 UNIQUE 是专门为练习设置的规则，真实任务应用可以允许重复标题。

## 什么时候该用什么

到这里你有了三种存数据的方式，怎么选？判断标准很简单——看你的数据会不会长大、要不要查询：

| 场景 | 用什么 | 理由 |
|------|--------|------|
| 几条配置、一点状态 | 文件 | 量小、不查询，文件最简单 |
| 要按条件查数据，但量不大 | SQLite | 能查询、零运维，一个文件搞定 |
| 多个程序同时读写、高并发 | 服务型数据库 | 需要评估写入竞争、网络访问、部署与一致性需求 |

关键认知是：这是“项目长大了才考虑”的事，不是“为了将来可能长大所以一开始就上”。先用最简单够用的方案，等它真痛了再换——这本身就是一条值得养成的工程判断。

可以用一个 Racket 式的类比把三种方式串起来，方便记忆：

![普通文件、SQLite 与服务型数据库的选择边界](/images/persistence-evolution.svg)

普通文件由应用负责解释数据格式；SQLite 将查询引擎嵌入应用；服务型数据库通过独立服务提供数据访问。图中三种方式不是 Racket 语法。

不管你最后用哪种，核心都回到那个本质：把数据组织成能被快速查询的表，用 SQL 这种声明式语言去对话。理解了这层，这些方案按需求选择，也可以在同一个系统中并存——而你现在已经站在能看懂全貌的位置了。

## 找问题，再改对

有人想按标题查任务，把用户输入直接拼进了 SQL：

```racket
(define (find-task conn title)
  (query-list conn
    (string-append
     "SELECT title FROM tasks WHERE title = '" title "'")))
```

正常输入它能跑。但传入 `it's` 试试——用户输入的单引号把 SQL 拦腰截断，查询直接报错；精心构造的输入甚至能改写这条 SQL 的本意。把拼接改成参数化：SQL 里放 `?` 占位，值作为独立参数另传。

参考答案：

```racket
(define (find-task conn title)
  (query-list conn "SELECT title FROM tasks WHERE title = ?" title))
```

占位符用于数据值，不用于任意 SQL 标识符。动态表名或排序字段需要使用预先限定的合法选择。
