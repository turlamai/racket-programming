# Loom——从零开发第一个 Web 应用

> 上一章我们已经知道，Web 程序接收 HTTP 请求并返回响应。本章使用 Loom 把这件事组织成一个可以逐渐扩大的应用。

## 从一个问题开始

假设你想做一个任务管理网站。浏览器访问首页时应该显示任务列表，访问某个任务的地址时应该显示它的详细信息。服务器怎么知道浏览器究竟想看哪一页？

浏览器发出的请求包含方法和路径。例如，GET /tasks/42 表示客户端希望读取路径 /tasks/42 对应的资源。服务器需要找到负责处理它的函数。把请求映射到处理函数的过程叫作路由（routing）。

Loom 是一个以 Racket 为中心的 Web 框架。本章使用它组织路由和生成 HTML；它建立在 Racket 的 web-server 之上，而不是另一种 HTTP 协议。

## 安装与版本说明

Loom 目前处于早期开发阶段，接口可能变化。以下示例依据 [Loom 源码](https://github.com/turlamai/loom) 的开发版本编写。暂不假定它已在 Racket Package Catalog 发布，也不假定完整的生产功能已经实现。

先安装 Racket 和 Git（Git 用于取得源码），打开终端：

```bash
git clone https://github.com/turlamai/loom.git
cd loom
raco pkg install --auto --name loom-dev --link "$(pwd)"
raco test loom/main.rkt
racket examples/hello.rkt
```

上面的路径写法适用于常见的 Unix shell；Windows PowerShell 可将最后一个安装参数写成 `(Get-Location).Path`。

打开浏览器访问 http://127.0.0.1:8080/。如果终端报告端口被占用，先停止占用端口的旧开发服务，或在自己的程序中通过 serve 的 #:port 参数指定其他端口。结束开发服务时，在终端按 Ctrl+C。

这里的 127.0.0.1 是回环地址，指向运行浏览器的这台计算机。这一步只是在本地学习，并没有把网站发布到互联网上。

## 写出第一个页面

新建 main.rkt，输入：

```racket
#lang racket/base
(require loom)

(define (home req)
  (html-response
   '(html
     (head (title "我的任务"))
     (body (h1 "今天要做什么？")))))

(define app
  (make-app
   (list (route #"GET" "/" home))))

(module+ main
  (serve app))
```

执行 `racket main.rkt`，在浏览器打开刚才的地址。

这里有四件事：

- home 是一个普通函数，参数 req 代表收到的请求。
- html-response 将 Racket 列表表示的 HTML 转换为 HTTP 响应。这种树形表示叫 xexpr，后面的第 57 章会详细解释。
- route 将 GET 方法和 / 路径关联到 home。注意 #"GET" 是字节字符串，不是普通字符串。
- make-app 根据路由列表构造处理请求的应用；serve 则启动服务器。

module+ main 让服务器在直接执行文件时启动，而不是在其他模块导入文件时立即启动。这为测试留下了空间。

## 让页面接收数据

再添加一个任务详情页。假设任务编号是路径中的一部分：/tasks/42。

在 home 和 app 的定义之间加入以下函数：

```racket
(define (task-detail req)
  (define id (route-param "id"))
  (html-response
   `(html
     (head (title "任务详情"))
     (body (h1 ,(string-append "任务 " id))))))
```

把 app 的定义替换为：

```racket
(define app
  (make-app
   (list (route #"GET" "/" home)
         (route #"GET" "/tasks/:id" task-detail))))
```

重新启动程序，访问 http://127.0.0.1:8080/tasks/42。页面应该显示“任务 42”。将地址中的 42 换成 99，观察页面如何变化。

:id 是一个路径参数占位符。Loom 在请求匹配时提取实际路径片段，route-param 再从当前请求的参数中取出它。反引号和逗号让我们能够在列表结构中插入计算结果，而不必手工拼接整段 HTML。

注意：这个示例只展示了编号，不代表数据库中真的存在这个任务。真实应用还需要查询数据、检查用户权限，并在任务不存在时返回相应的错误响应。

## 观察 HTTP 的行为

不妨在另一个终端中运行以下命令（Windows 下如果 curl 是 PowerShell 的别名，请使用 curl.exe）：

```bash
curl -i http://127.0.0.1:8080/tasks/42
curl -i http://127.0.0.1:8080/missing
curl -i -X POST http://127.0.0.1:8080/tasks/42
```

依据本章所用接口，三个请求应分别得到 200、404 和 405。200 表示请求成功，404 表示没有找到匹配路径，405 表示该路径不接受请求使用的方法。这样，我们不仅观察页面是否出现，还验证了服务器对不同请求的处理结果。

## 把业务逻辑留在 Racket 中

回想前面的 GUI 章节：一个任务首先是数据，不是屏幕上的矩形。在 Web 应用里也是如此。我们可以继续使用结构体、纯函数和 RackUnit 测试表达任务的规则，再让 Loom 处理请求、调用函数并生成页面。

当同一个应用还需要桌面版本时，Glaze 和 Rivet 可以采用同样的业务逻辑。不同的是界面和交互入口，而不是任务本身的定义。

## 接下来学什么

本章仅使用开发版本已提供的路由、HTML 响应和本地服务接口。数据库迁移、表单、会话、认证及实时组件仍属于 Loom 的演进方向，不能把路线图当成已经可用的功能。

Racket 还有 Koyo 等 Web 工具包；不同框架解决的工程问题并不完全相同。理解 HTTP、数据模型和函数组合之后，学习其他框架也会容易很多。

练习：增加一个 /about 页面，再尝试访问不存在的路径。思考如何将任务数据从处理函数中分离出来，使相同的数据逻辑能独立运行和测试。

下一章讲解服务器如何通过 Nginx 对外提供服务。那是通用部署知识，不意味着当前 Loom 开发版本已经具备生产上线条件。
