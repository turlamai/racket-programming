# 稳定上线——给 Racket Web 程序配好 Nginx

> 写好的 Racket Web 程序怎么对外服务？答案分两层：Racket 在本机一个端口上稳定响应 HTTP，剩下的——HTTPS、反向代理、静态资源可以交给 Nginx，而进程守护由 systemd 等服务管理器负责。这篇把这条最省心的部署路线完整走一遍。

不假设你熟悉运维，只假设你已经：

- 能用 Racket 写一个 Web 程序（`web-server` 或类似框架）
- 能在服务器上运行 Racket 程序

## 为什么需要 Nginx

很多人会直接这样做：

```bash
racket main.rkt
```

然后让程序监听 `0.0.0.0:8000`，再直接通过 IP 访问。

这 **可以跑**，但很多正式部署仍会在前面放一层反向代理，原因主要是工程分工：

- 集中处理 HTTPS、证书续期和安全相关 Header
- 统一处理反向代理、访问日志、限流、缓存等入口策略
- 静态资源可以交给专门的 Web 服务器或 CDN
- 后端只监听回环地址，避免直接暴露应用端口
- 需要时可以在多个 Racket 实例之间做负载分发

这里不需要假设 “Racket Web Server 天生扛不住并发”。是否需要 Nginx，应该由部署需求、基准测试和运维约束决定。

**Nginx 的角色是：**

- 作为对外的 Web 入口（80 / 443）
- 处理 HTTPS、反向代理、静态资源
- 把请求转发给后端的 Racket 程序

以下是通用部署模型，不是 Loom 开发预览示例的生产上线指南。Loom 示例默认端口为 8080；本章独立示例使用 8000。

经典结构如下：

```text
[ Browser ]
 |
 v
[ Nginx ] :80 / :443
 |
 v
[ Racket Web ] :127.0.0.1:8000
```

## 一个最小可部署的 Racket Web 程序

我们先准备一个 **最简单但规范** 的 Racket Web 服务。

**1. 示例代码**

```racket
#lang racket

(require web-server/servlet
 web-server/servlet-env
 web-server/http)

(define (start req)
 (response/xexpr
 `(html
 (head (title "Racket + Nginx"))
 (body (h1 "Hello from Racket")))))

(serve/servlet start
 #:port 8000
 #:listen-ip "127.0.0.1"
 #:servlet-path "/"
 #:launch-browser? #f)
```

**几个关键点：**

- `127.0.0.1`：只监听本机回环地址，减少直接暴露，但不能替代认证、授权和应用安全
- 固定端口：便于 Nginx 转发
- 不自动打开浏览器

运行后，本机访问：

```text
http://127.0.0.1:8000
```

## Nginx 的核心概念（够用版）

在部署 Racket Web 时，你只需要理解三件事：

### 反向代理（reverse proxy）

Nginx 接收请求 → 转发给 Racket → 再把响应返回给客户端。

### upstream（可选）

当你有多个后端实例时使用，新手可以先不用。

### location

用来匹配 URL 路径，并指定处理方式。

## 最小 Nginx 配置（HTTP）

以下命令以 Debian/Ubuntu 的 Nginx 与 systemd 布局为例。example.com 是占位域名，实际操作前换成自己控制的域名，确认 DNS、端口与防火墙配置。

假设你的 Racket 程序运行在：

```text
127.0.0.1:8000
```

### 创建站点配置

```bash
sudo nano /etc/nginx/sites-available/racket-app
```

### 基础配置内容

```nginx
server {
 listen 80;
 server_name example.com;

 location / {
 proxy_pass http://127.0.0.1:8000;

 proxy_set_header Host $host;
 proxy_set_header X-Real-IP $remote_addr;
 proxy_set_header X-Forwarded-For $remote_addr;
 proxy_set_header X-Forwarded-Proto $scheme;
 }
}
```

本例假定 Nginx 是唯一对外代理，因此覆盖客户端传入的 X-Forwarded-For。若前面还有 CDN 或负载均衡器，应配置可信代理地址与真实 IP 解析规则；不能直接信任客户端自报的代理头。

### 启用配置

```bash
sudo ln -s /etc/nginx/sites-available/racket-app /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
```

现在访问：

```text
http://example.com
```

请求路径为：

```text
Browser -> Nginx :80 -> Racket :8000
```

## HTTPS（Let's Encrypt）

现实部署中 **强烈建议使用 HTTPS**。

### 安装 Certbot

```bash
sudo apt install certbot python3-certbot-nginx
```

### 自动配置证书

```bash
sudo certbot --nginx -d example.com
```

Certbot 会：

- 自动修改 Nginx 配置
- 添加 443 端口
- 配置证书路径
- 设置 HTTP → HTTPS 跳转

还需检查应用是否正确处理 HTTPS 外部地址、Secure cookie 与可信代理头。证书签发需要域名及相应验证条件。

## 静态资源交给 Nginx

静态资源可由 Racket、Nginx 或 CDN 提供；按部署需求选择。下面演示 Nginx 静态目录。

### 项目结构示例

```text
app/
 ├─ main.rkt
 └─ static/
 ├─ style.css
 └─ app.js
```

### Nginx 配置静态目录

```nginx
location /static/ {
 alias /opt/racket-app/static/;
}
```

确保 Nginx 工作进程具有该静态目录的读取与目录遍历权限；不应把数据库、密钥或源码目录整体作为静态资源发布。

### Racket 中引用

```html
<link rel="stylesheet" href="/static/style.css">
```

这样：

- `/static/*` → Nginx 直接返回
- `/` → Racket 处理

性能和结构都会更清晰。

## Racket 程序如何长期运行

### 不要用 SSH 会话跑

错误示例：

```bash
ssh server
racket main.rkt
```

### 使用 systemd（推荐）

创建服务文件：

```bash
sudo nano /etc/systemd/system/racket-app.service
```

```ini
[Unit]
Description=Racket Web Application
After=network.target

[Service]
User=racketapp
WorkingDirectory=/opt/racket-app
ExecStart=/usr/bin/racket /opt/racket-app/main.rkt
Restart=on-failure
RestartSec=3
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

先由管理员创建专用低权限账户 racketapp，部署代码到 /opt/racket-app，确认该用户能读取代码并仅能写入指定数据目录。确认 racket 的实际安装路径。以下命令适用于使用 systemd 的 Linux；Nginx 目录布局和 Certbot 安装方式以发行版为准。

启动服务：

```bash
sudo systemctl daemon-reload
sudo systemctl enable racket-app
sudo systemctl start racket-app
```

## 部署验证

先检查后端，再检查代理层：

```sh
curl -i http://127.0.0.1:8000/
sudo systemctl status racket-app --no-pager
sudo journalctl -u racket-app -n 50 --no-pager
sudo nginx -t
curl -i -H 'Host: example.com' http://127.0.0.1/
```

域名和证书配置完成后，再通过实际域名的 HTTPS 地址验证。不要把证书检查失败当作正常现象而关闭客户端验证。公开部署还需要设置请求大小限制、超时、访问日志、数据备份及升级回滚流程；本章仅给出基础结构。

## 常见问题与排查思路

### 浏览器 502 Bad Gateway

- Racket 程序是否在跑？
- 端口是否一致？
- 是否监听在 `127.0.0.1`？

### 访问慢

- 静态资源是否仍由 Racket 提供？
- 是否需要并正确配置 gzip / Brotli 等压缩

### 路径不对

- `proxy_pass` 是否带 `/`
- Racket 是否假设根路径为 `/`

## 部署的心智模型

作为 Racket 开发者，你可以这样理解：

- **Racket**：业务逻辑、状态、规则
- **Nginx**：入口代理、TLS、静态资源和运维策略

你只需要保证：

> Racket 程序在本机一个端口上 **稳定响应 HTTP**

Nginx 不会替应用实现认证、授权、CSRF 防护、数据库备份或业务限额。还需要可信代理头策略、进程管理、日志和监控。

## 结语

Nginx 并不是 Racket 的对立面，而是它在生产环境中的 **天然搭档**。

一旦你掌握了这个部署模式，你会发现：

- 本地代码与服务器代码可以共享业务逻辑，但权限、网络、证书、数据目录和运行环境需要独立验收
- Racket Web 完全可以胜任严肃的服务端工作

这正是 Racket 作为「可扩展语言」在工程实践中的价值所在。
