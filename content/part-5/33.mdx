# Rivet——共享业务逻辑与平台原生界面

> Rivet 的跨平台共享发生在业务逻辑和接口契约上，而不是把同一套控件代码运行在每个平台。本章通过 Taskboard 学习如何安排这些边界。

第 32 章的计数器已经验证了原生窗口与 Racket 后端的基本连接。现在我们将它扩展到任务管理问题。这里沿用上一章关于任务、输入验证、草稿与已提交状态的概念，但 Glaze 和 Rivet 的官方示例是独立实现，并不共享同一个实际源码文件或数据格式。

## 运行 Taskboard

从 [Rivet 项目仓库](https://github.com/turlamai/rivet) 进入 examples/taskboard。按其 README 安装对应版本的依赖后，在示例目录运行：

```sh
raco rivet doctor
raco rivet schema check rivet-schema.json --json
raco rivet dev
```

关闭窗口后运行 raco test tests/backend.rkt。这个测试针对真实的 RVT1 后端通信路径，不等于所有原生界面交互已经通过测试。

## 数据契约

打开 app/backend.rkt。真实示例定义了任务状态和记录：

```racket
(define-enum TaskStatus (backlog active done))

(define-record BoardTask
  ([id : Int64]
   [title : String]
   [notes : String]
   [status : TaskStatus]))
```

这是从实际模块摘出的声明，需要在原模块的 rivet/backend 环境中使用。TaskStatus 枚举把合法状态限定在待处理、处理中和已完成三个值。BoardTask 则描述跨语言传递的字段。字段的类型、名字及顺序是通信契约的一部分，而不是随意的实现细节。

## 查询和修改不是同一件事

真实示例的任务列表状态与查询 RPC：

```racket
(define-state tasks : (List BoardTask) initial-tasks)

(define-rpc (list-tasks : (List BoardTask))
  (state-ref tasks))
```

initial-tasks 是原模块中定义的初始任务列表。list-tasks 返回当前状态；create-task、update-task、delete-task 负责变化。task-saved 事件用于报告保存行为。阅读这些声明，可以看到界面所能调用的操作以及可观察的状态。

## 跟踪一次编辑

用户修改标题时，界面先维护自己的草稿。点击保存后，生成的客户端调用后端 RPC。Racket 检查标题、任务 ID 与其他约束，再更新持久化快照和共享状态。

当前官方示例在真实启动路径启用存储，先保存快照，再提交可见状态；写入错误返回 RPC 失败。测试可以使用独立的临时存储环境。这里的行为与 Glaze 示例的延迟自动保存策略不同，不能直接互换两者的持久化语义。

窗口收到失败时应保留草稿；收到成功后再更新显示。不要让用户为了重试而重新输入整段内容。

## 选择本机的界面源码

Windows 使用 windows/MainWindow.xaml 及其 C++ 实现；macOS 使用 macos-host/Sources/RivetHost/ContentView.swift；Linux 使用 linux/src/main.cpp。

先找到现有的列表、详情和保存动作。不要手写 RVT1 数据帧，也不要猜测生成客户端的方法名称：在构建后阅读当前版本生成的 API。Swift 的记录和枚举位于 RivetTypes 下，C++ 采用生成的接口与完成回调。

一个适合初学者的改动是编辑后端 initial-tasks 中的某个标题，然后用测试和本机窗口验证。已有持久化数据可能覆盖初始任务，需使用新的隔离目录（RIVET_TASKBOARD_DATA_DIR）验证初始化行为。

## 持久化的提交边界

阅读 app/backend.rkt 中的 commit-board!。它使用 board-write-lock 串行化修改，在锁内计算候选列表，并在短暂禁用 break 的范围内执行以下操作（摘录，依赖原模块定义）：

```racket
(parameterize-break #f
  (when storage-root
    (write-task-snapshot! storage-root next-task-id
                          (map task->row candidate)))
  (state-set! tasks candidate))
```

先写入候选快照，再发布共享状态。写入失败会阻止后续 state-set!。这里禁用 break 是为了减少取消信号在两个提交动作之间打断计算的风险，并不等于数据库事务，也不能保证突然断电时数据一定保存。存储实现、文件系统及进程间协调仍有各自的边界。

阅读 create-task 和 update-task，可以看到标题和备注通过 validate-text 去除首尾空白并检查长度，标题不可为空，备注允许为空，两者上限均为 4000 个字符。这是业务校验，不应与 String 类型约束混为一谈。任务 ID 可能在后续校验失败或取消之前已经分配，因此 ID 出现间隔不代表任务丢失。

## 耗时操作与取消

官方示例还演示了 Generate 1,000 与 Cancel。生成任务时，后端发出进度事件；取消请求时，框架处理请求的生命周期。generate-demo-tasks 将数量限制在 0 到 1000，构造候选列表期间发送 operation-progress 事件，最后通过 commit-board! 替换整个任务列表。生成期间取消不会提交半成品，但已经分配的 ID 不会自动恢复；如果取消发生在提交完成后，也不能假定已提交数据会回滚。请使用隔离数据目录，因为该操作会替换原有列表。

这并不意味着所有任意 RPC 都天然具有事务性或可取消性。开发者仍须设计安全的提交点、资源关闭策略和副作用边界。

## 进阶阅读：实时曲线的数据通路

当前源码还包含一个独立的模拟实时曲线案例。timing-ticker 生成模拟时间偏差和延迟数据，经 chart-series-append! 写入容量为 8192 的序列，再按每三个采样步骤合并并发送 chart-batch 事件。timing-window RPC 可提供初始窗口和补充历史数据。这里的数据来自合成函数，不是真实设备测量，sleep 11/1000 也不是精确实时采样保证。

这一案例适合进一步理解三种接口的区别：RPC 用来主动查询或发起操作，State 表达当前共享状态，Event 传递进度或增量数据。高频数据不应简单地为每个样本触发一次完整界面重绘。实际吞吐量、时间戳精度、批次丢失后的恢复及后台线程的停止行为需要独立测试。

## 接口演进

修改普通任务标题不会改变通信契约。如果新增字段、RPC 或枚举值，则应先检查兼容性，再根据意图更新基线：

```sh
raco rivet schema check rivet-schema.json --json
raco rivet schema --output rivet-schema.json
git diff -- rivet-schema.json
```

不要为了让 CI 通过而无条件刷新基线。构建和验收还需要各目标平台的原生工具链。

## 练习与验收

回顾第 31 章的纯任务函数，思考哪些业务规则可以完全脱离窗口测试。然后在当前平台找到任务编辑入口，追踪从界面事件到 RPC，再到状态显示的完整路径。

参考验收：在隔离目录创建任务，保存后重启检查；尝试空标题，确认错误且草稿保留；将 Generate 1,000 操作与取消配合测试，检查取消前后的列表以及 ID 分配行为；记录当前平台实际表现，不能将一个平台的测试结果当作三个平台均已通过。
