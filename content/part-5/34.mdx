# GUI 并发、测试与发布——让应用稳定运行

> 窗口能打开不代表应用已经完成。还需要保证耗时操作不会阻塞交互，失败时能恢复，关闭时能释放资源，并在实际目标平台验证安装产物。

前面我们使用三种技术路线开发桌面应用。本章讨论它们共有的工程问题。无论界面由什么框架渲染，用户都希望点击有响应、数据不会因失败而丢失、关闭窗口后程序能合理退出。

## 为什么窗口会卡住

界面通常有负责处理输入、布局和绘制的事件循环。如果一次按钮回调长时间占用它，后续事件就不能及时执行。把计算放到后台，并将结果提交给界面，是解决这类问题的常用方式。但并发不必然意味着多核并行，也不保证任务本身变快。

## racket/gui：从最小例子理解后台工作

保存为 responsive.rkt：

```racket
#lang racket/gui
(define f (new frame% [label "后台任务"] [width 320]))
(define p (new vertical-panel% [parent f]))
(define status (new message% [parent p]
                    [label "就绪"] [auto-resize #t]))

(new button%
     [parent p]
     [label "开始"]
     [callback
      (lambda (button event)
        (send button enable #f)
        (send status set-label "处理中")
        (define es (current-eventspace))
        (thread
         (lambda ()
           (define result
             (with-handlers ([exn:fail?
                              (lambda (e)
                                (string-append "失败：" (exn-message e)))])
               (sleep 2)
               "完成"))
           (parameterize ([current-eventspace es])
             (queue-callback
              (lambda ()
                (send status set-label result)
                (send button enable #t)))))))])
(send f show #t)
```

运行 racket responsive.rkt。点击开始后，按钮暂时禁用，模拟任务在后台运行，最后通过 queue-callback 将界面更新排入原来的 eventspace。这里 sleep 只是演示等待，不代表真实的业务计算。

这段代码刻意避免重复启动任务，但没有实现关闭窗口时的取消协议。真正应用应跟踪工作任务的生命周期，避免窗口已销毁后仍提交更新，并在退出时进行资源清理。第 24 章介绍了 Custodian。

同步 channel 的发送和接收可能阻塞，不应直接在界面回调中等待。GUI 的 yield 可以在等待同步事件时派发其他事件，但会引入重入风险；初学者优先采用后台任务加结果回调的方案。不要将这里的 yield 与第 37 章生成器的 yield 混淆。

## Glaze：异步调用不等于后台计算

第 30 章的 JavaScript 使用 await 等待生成的 API。这样可以在等待结果时让页面继续处理其他事件，但并不自动保证 Racket 后端执行并行，也不会替你解决共享状态的并发写入。

第 31 章的 Taskboard 在后端使用信号量串行化状态更新。耗时任务还需要结合当前 Glaze 版本提供的事件、生命周期及取消机制，明确失败和退出时的行为。页面应显示处理中状态，限制重复提交，并保留失败的输入。

## Rivet：遵守原生界面线程规则

第 33 章的 Taskboard 使用生成的客户端调用后端。长任务通过进度事件报告状态，并演示取消。Windows、macOS 和 Linux 的界面更新要遵守各自 UI 框架的线程约束，不能把 Racket 的 queue-callback 直接搬到这些原生宿主中。

取消与保存之间必须设计明确的提交点：未提交的任务可以丢弃；已经完成的持久化操作不能假装没有发生。取消不等于自动回滚所有副作用。

## 如何证明一个应用可用

将测试分成不同层次：

| 层次 | 要验证的行为 |
|---|---|
| 领域逻辑 | 输入校验、任务完成规则、统计结果 |
| 接口契约 | 参数与返回值类型、错误、兼容性 |
| 持久化 | 保存、重新加载、损坏文件、写入失败 |
| 界面 | 键盘操作、缩放、焦点、错误恢复 |
| 安装产物 | 全新环境安装、启动、卸载与适用的升级流程 |

先用 raco test 验证不依赖窗口的代码，再检查框架接口及真实窗口。最后在目标平台安装构建产物，而不是只测试开发目录。

## 从运行到分发

Glaze 的基本命令：

```sh
raco glaze doctor --json
raco glaze schema check --json
raco glaze verify
raco glaze build --name myapp
```

Rivet 的基本命令：

```sh
raco rivet doctor
raco rivet schema check rivet-schema.json --json
raco rivet build
raco rivet package
raco rivet verify
```

请在对应项目目录运行。verify 的具体检查范围随框架及项目配置而定，不能替代完整业务验收。签名、安装器、更新渠道、目标架构和依赖版本应参考各框架当前官方发布文档。不要把开发构建直接当作生产发布。
